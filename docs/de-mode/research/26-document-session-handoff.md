## Session interface

```ts
createSession(raw: {
  bytes: Uint8Array | ArrayBuffer; // Buffer works as Uint8Array in CommonJS
  documentId: string;             // nonempty backend open-document identity
  path: string;                   // nonempty opaque original path
  formatHint: string | null;      // required; never certifies content
}, ownerId: string): Session

interface Session {
  read(): State;
  replaceScalar(expectedRevision: number, path: (string | number)[], value: D1Scalar): State;
  undo(expectedRevision: number): State;
  redo(expectedRevision: number): State;
  snapshotForSave(expectedRevision: number, destination: string): Promise<SaveSnapshot>;
  acknowledgeSave(snapshot: SaveSnapshot, receipt: SaveReceipt): State;
}
```

`ownerId` is deliberately one nonempty opaque **primitive string**, supplied by
the authenticated desktop/core. Mutable owner objects are rejected. The backend
must assign an identity that captures its actual context lifetime/epoch and a
document ID unique to that open; identities must not be recycled across active
or late operations. The session retains only immutable primitive metadata and
D1's copied bytes. It does not choose roots/editions, decode a context tag,
revalidate leases or authorize writes. Adapting the eventual core context DTO
into this opaque ID is **required host work**, not a second context policy here.

`createSession` synchronously calls D1's classifier, retaining its document,
assessment and content kind. Recognition stays stable under scalar-only edits;
the session does not implement a second classifier.
Decoded-text input is unsupported. Invalid syntax/encoding/limits throw D1's
original error, with opaque recovery bytes; no partially editable session is
created. Any valid JSON can be preserved, including generic/wrong LORD shape.
A filename or format hint never selects a converter or proves compatibility.

`read()` returns a frozen record with these fields:

- Identity/source: `documentId`, `ownerId`, immutable original `sourcePath`,
  current committed destination `path`, original `formatHint`, content `kind`
  (`de-lordjson`, `ambiguous-lordjson` or `generic-json`).
- D1 state: `originalDocument`, current `document`, `savedDocument`, frozen
  `assessment` and its `diagnostics`. Each document has D1's immutable ordered
  nodes and `serialize()` returning a fresh byte copy. No object projection is
  created for serialization.
- History/save state: `revision`, `savedRevision`, `dirty`, `canUndo`, `canRedo`,
  `save` and `lastSave`. `save` is null or a frozen `{status,snapshot}`; status is
  `preparing`, `pending` or `unknown`. During preparation `snapshot` is null.
  `lastSave` is null or frozen `{status,snapshot}` from the last matched receipt.

On open, current/original/saved document are identical, both revisions are 0,
`path === sourcePath`, and `dirty === false`. `dirty` compares **exact bytes**
with the last committed/open content, not document identity or revision equality.
Undo or a real edit back to those same bytes can therefore become clean.
`sourcePath` always records the original open path; successful Save As changes
only `path`. Undo/redo never change destination.

`replaceScalar` uses D1's atomic unique-path scalar patch. It accepts the same
strings/booleans/null/safe Numbers/BigInts/`losslessJson.numberToken(lexeme)`;
callers use that environment's numberToken factory. Missing paths, ambiguous
decoded ancestors/keys, containers and invalid values fail through D1. No
insertion, deletion, reorder, key replacement, defaults, normalization or
structural batch/session framework is added. Target diagnostics do not prohibit
an unambiguous edit or preservation save.

Each real edit/undo/redo advances the **session content revision** monotonically.
This is distinct from `document.revision`, which can repeat after branching.
All content commands require the exact current safe-integer session revision;
stale/invalid expectations throw `SessionError` with `code:'stale-revision'`.
Valid no-ops retain document identity, byte spelling, revision, dirty state and
undo/redo history. Undo/redo at a history boundary are likewise no-ops after the
revision check. A real edit after undo discards only that redo branch. Failed
edits publish no state. Safe-integer exhaustion fails explicitly. Saves do not
advance the content revision or insert history entries.

## Save snapshots, receipts and reconciliation

`snapshotForSave` always requires an explicit nonempty opaque destination string;
ordinary Save can pass `read().path`, while UI chooses Save As's destination.
No path canonicalization or destination authorization belongs here. The method
checks revision and reserves the one save slot **before** awaiting SHA-256.
It captures the then-current immutable document and bytes; edits/undo/redo may
continue during hashing or the eventual backend write.

The returned frozen snapshot contains:

```ts
{
  saveId: number;       // monotonically increasing within this session
  documentId: string;
  ownerId: string;
  revision: number;     // submitted session revision
  destination: string;
  sha256: string;       // lowercase hex, platform SHA-256 of exact submitted bytes
  byteLength: number;
  serialize(): Uint8Array; // fresh copy each call
}
```

Retained snapshot bytes are private. No TypedArray is exposed as immutable via
shallow freeze. The active entry retains the exact snapshot object identity and
captured D1 document, so a spread clone, forged snapshot, other session's
snapshot or already-settled snapshot is rejected with `foreign-snapshot`.
Changing a public byte copy cannot change retained bytes, digest or saved state.
The digest is not an authenticity signature.

The adapter submits `snapshot.serialize()` as opaque bytes and keeps the exact
snapshot reference associated with the backend's authenticated operation. A
receipt is a plain envelope containing **all seven metadata fields** above
(`saveId, documentId, ownerId, revision, destination, sha256, byteLength`) and
`status:'committed'|'failed'|'cancelled'|'unknown'`. It contains no `serialize`
method. Every metadata field must equal that snapshot; missing/changed metadata
or unsupported outcome throws `receipt-mismatch` and leaves state unchanged.
The backend must return/confirm the digest and exact committed destination;
the session never accepts a different canonical path silently.

- `committed`: means the backend confirms that exact write completed. Sets
  `savedDocument`, private saved bytes and `savedRevision` from the snapshot,
  changes `path` to its destination, then recomputes dirty against **current**
  content. Later differing edits remain dirty and all history/current bytes
  survive. A matching older receipt is not a command to replace the editor.
- `failed` / `cancelled`: mean a known noncommit. Preserve original/current/saved
  content, revisions, history, dirty state and prior destination; release the
  save slot. Cancellation of a dialog should normally precede snapshot creation.
- `unknown`: makes no success claim and preserves all those states. Retains the
  snapshot and save slot with explicit unknown status. Another snapshot is
  refused with `save-in-flight`. The backend/UI must reconcile the **same**
  operation and feed that snapshot another matching final receipt (or another
  unknown). This module never retries/replays a write or infers success from a
  timeout, missing response or cancelled transport.

A digest preparation failure rejects the promise, releases the slot and keeps
all document/destination/saved state; no write was issued by this module. While
unknown, edits and undo/redo remain available but new saves remain blocked.
There is no automatic timeout success, abandonment or recovery clone in Rust.
The host must distinguish cancellation before write acceptance from an uncertain
outcome after acceptance. `saveId` is a correlation sequence, not backend lease
authority. The envelope checks cannot authenticate a caller that fabricates a
fully matching receipt; only the actual host/core may decide write outcomes.

### DS1-R1-01 response: finite session-owned history

API additions, identical in CommonJS and browser globals:

```ts
// Exported frozen defaults; callers may only tighten these limits.
DEFAULT_HISTORY_LIMITS = { maxEntries: 32, maxBytes: 16777216 };
declare function createSession(raw: RawDocument, ownerId: string, options?: {
  historyLimits?: { maxEntries?: number; maxBytes?: number }
}): Session;
// Additional frozen read() field:
history: {
  limits: { maxEntries: number; maxBytes: number };
  entries: number;
  byteLength: number;
};
```

`maxEntries` counts the complete undo/current/redo list, **including current**:
32 entries allow at most 31 undo/redo steps combined. `maxBytes` is the sum of
D1 `document.byteLength` across that list, in source UTF-8 **bytes**, including
current. Each distinct document reference occurs once in this list; moving
between undo and redo does not add a reference or change its summed cost.
Both limits apply simultaneously. Limits are copied/frozen primitive values;
unknown keys, unsafe/noninteger values, `maxEntries` outside [1,32] and
`maxBytes` outside [0,16777216] throw TypeError before session creation.

A real scalar edit builds one bounded D1 candidate, discards redo, then evicts
oldest undo entries until both limits hold. The current document is mandatory:
if it alone exceeds a tightened byte cap, it stays as the sole history entry,
with `history.byteLength` honestly above that cap and no undo/redo. The default
16 MiB cap exceeds D1's default 8 MiB per-document cap, so this exception is only
needed for tighter caller limits. No-op edits and boundary undo/redo preserve
history, revision and bytes exactly. Failed/stale edits publish no state or
partial eviction. Undo/redo keep the already-bounded list; saves add no history.
Branching releases the entire discarded redo list before retention accounting.

The byte allowance is **not an estimate or exact measurement of JS heap/RSS**.
It bounds retained source-byte cost alongside an explicit document count;
D1 independently caps each document's tokens/nodes/depth/strings. Original,
current, saved and active preparing/pending/unknown documents are mandatory
references and remain valid even after their history entries are evicted.
Current is already in the list; original/saved/active may alias it or each other,
or pin at most three additional distinct documents outside it. They are not
added repeatedly to history cost. Their D1 default limits still apply. Saved
comparison bytes, one active save's bytes and the latest receipt snapshot's
bytes are separately bounded by those per-document limits; aliases can share
these buffers. Digest/serialize/candidate work makes temporary bounded copies.
This is a component retention policy, not an exact process-memory ceiling.

Caller-retained `read()` records, public D1 documents, byte copies, error recovery
bytes and old public save snapshots can keep additional data alive outside the
session's control. Consumers must release their own references. This component
cannot bound arbitrary caller-held snapshots. No generic history framework,
second parser or host resource policy was introduced.

Saved-content behavior remains byte-based: an evicted saved document stays
pinned, and an older committed snapshot marks only its submitted bytes saved.
Later edits during preparing/pending/unknown remain valid and dirty when their
bytes differ. Editing a newly created document back to the submitted bytes can
be clean after reconciliation even though its document/session revisions differ.
