## Decision and evidence

**Use one host-independent Rust backend core, linked into Tauri and called by Electron through one small bundled helper. Keep lossless documents and their sessions in one shared JavaScript implementation.** Separate Classic and DE providers by edition and format; share contracts and authority, without inventing a universal game format. Preserve both hosts and Classic behavior.

This fits the inspected repository:

- [F1 Rust](../../../src-tauri/src/profiles.rs) already has no Tauri dependency: production imports are std, serde/serde_json, sha2 and dunce. It and [F1 Node](../../../src/node/game-profiles.js) independently implement PE/layout detection, metadata parsing and the same journal. Three correction rounds demonstrate the maintenance cost. Round3 reports 97 Node/26 Rust tests; correctness closure remains pending. Keep its evidence, rather than another production port.
- [Host dispatch](../../../src-tauri/src/desktop.rs) captures global installation state inside queued work; [Electron](../../../main.js) similarly reads saved roots and separately accepts library `gameRoot`. These must consume one context policy. Critique21's phrase “two host implementations” can justify two transports, but cannot override the later prohibition on duplicate policy.
- [Packaging](../../../package.json) ships Electron with ASAR and config `extraFiles`; it currently has **no helper build/resource**. [Native packaging](../../../scripts/package-native.mjs) already requires Windows x64. [The frontend builder](../../../scripts/build-desktop.mjs) excludes `src/shared/` from copied payloads, expecting bundling: new document modules need an explicit frontend entry/import. Rust DTO generation already exists in [contracts.rs](../../../src-tauri/src/desktop/contracts.rs).
- [A1](../../../crates/de-assets-core/README.md) is a standalone std-only Rust crate, absent from the app graph. Its reported 29 synthetic tests and 86-object local parity cover metadata, not pixels. Its Windows local-NTFS file resolver and cancellation handle favor native reuse; they do not make decoding complete or block LORDJSON editing.

**Feasible alternatives.** A Rust Node-API addon could call the same core in-process from Electron, avoiding process startup and wire copies. It adds a native binding/toolchain and architecture packaging matrix, async/cancellation glue, and brings decoder crashes into Electron main; investigate only if measured helper overhead is material. A shared WASM policy module is also feasible if it owns detection, metadata parsing, context transitions **and the complete recovery/transaction state machine**, with hosts executing mechanical I/O instructions. Generating constants or keeping two journal implementations does not qualify. That approach rewrites the corrected imperative F1 filesystem protocol and still needs native A1 access. The helper reuses more reviewed behavior and avoids either embedding Node in Tauri or adding a JS engine to Rust. None of these costs justifies dropping Electron.

## Ownership and dependency map

```text
Both renderers -> shared JS document session -> D1 JSON/LORD overlay
Tauri adapter  ---------------------------> toolkit-core (in-process)
Electron main -> versioned private helper -> toolkit-core (same Rust source)
 toolkit-core: profiles + context/leases + byte I/O + edition dispatch
 providers: Classic compatibility | DE -> de-assets-core (after review)
 Rust contracts -> generated TS; schema JSON -> generated LORD guard
```

**Installation/persistence/context:** `toolkit-core` alone owns canonical root/edition identity, detection evidence, metadata validation/migration/recovery/CAS, default selection, startup/inheritance rules, staged activation, leases and cache namespaces. Hosts supply the platform app-data base; one core resolver selects `AI Toolkit` or the explicit `AI_TOOLKIT_USER_DATA` override, consistently across hosts. Keep `game-profiles.v1.json` and its existing journal protocol. Whole-store CAS stays private. Only explicit activation changes `defaultProfileId` and `selectedByEdition`, together. Startup uses a freshly validated default; the migrated Classic candidate requires the unchanged legacy-source hash and matching identity specified in synthesis03. Otherwise bind standalone with diagnostics. Inheritance gets a fresh epoch and never reruns default selection.

**Thin adapters:** authenticate the actual `WebviewWindow`/`event.sender`, register its core owner, collect dialog choices, schedule blocking work, carry bytes, project errors/events and manage native window/process lifetime. They do not select editions, validate profile stores, recover transactions, calculate capabilities or re-read global roots. Every game/library/config/skin/document operation resolves an immutable lease before worker scheduling. Reject conflicting legacy root arguments. Keep a publication check against that lease after asynchronous work. UI owns edit freeze, unsaved prompts and adoption; core stops admission, drains accepted writes and revalidates/commits activation. A lost activation reply is queried by activation ID before UI adoption or retry.

**Documents:** keep `src/shared/lossless-json.js` and `src/js/de-lord-format.js` as D1's single implementation. Add one renderer-side session module owning original/current documents, revision, undo, saved revision, format, explicit destination and owner context. Both hosts load that module; `runtime.ts` remains transport state. Rust carries opaque bytes and performs the leased atomic write; it does not parse/re-emit LORDJSON. Save completion marks only the submitted revision saved; failed/cancelled/unknown-outcome saves retain bytes, undo and destination. DE never passes through `character-editor.js` template normalization or `castle-format.stringify`. Keep Classic binary AIV and UCP Character adapters as distinct formats, and later DE AIVJSON as an ordered-program overlay over D1.

**Providers/assets:** dispatch on the bound edition once, then on operation/format capability. A DE request cannot fall back to Classic GM1/UCP. A1 supplies DE metadata now; later native decoders live once under that DE provider, with bounded work and explicit unsupported formats. Renderer owns composition/facing. Detection fingerprint, provider resource identity, configuration revision and document revision are different values. Cache keys include profile, provider/decoder revision and relevant resource identity; F1's binary `sourceRevision` is not an atlas fingerprint. Persistent asset caches await A1's reviewed source-manifest contract.

Existing Classic Node/Rust game implementations remain an explicit **temporary duplication**, not evidence that SSOT is finished. Keep them behind visibly Classic adapters during the first document slice. Then extract the existing Tauri `game/` implementation into the Classic core provider, migrate one Electron operation at a time against current Node outputs, and retire each replaced Node runtime path. The inspected Rust game modules use no Tauri APIs, making this smaller than a rewrite. Preserve host-specific availability (Electron currently lacks Tauri's unit-sprite API), cache behavior and exports; resolve observed parity differences before cutting over. Do not make this entire migration a prerequisite for LORDJSON.

**Schema/DTO truth:** `config/de-lord-schema.json` becomes the only maintained LORD inventory. Today `de-lord-format.js` manually repeats `pinnedNames`, `pinnedArrays`, provenance, counts and initializer rules; this is a second runtime inventory, even though it protects valid reviewed invariants. Generate that expected guard from the JSON, retaining private snapshots, deep freezing and exact mutation rejection. Generated output is checked, never edited; neither runtime independently maintains fields. Keep `tests/de-lord-format.test.js`'s independent reviewed 118-field/14-array oracle: test evidence may disagree with a generated artifact and block a bad source update. Regeneration is not source approval. Rust serde enums/DTOs remain the authority for both transports, with ts-rs output and exhaustive operation/result maps. Encode A1 signed-i64 IDs as decimal strings at the wire boundary; the existing global `with_large_int("number")` must not round them.

The shared JS session exposes `createSession(raw, owner)`, `replaceScalar(expectedRevision, path, value)`, `snapshotForSave()` and `acknowledgeSave(snapshot, receipt)`. A save snapshot carries document/owner IDs, revision, destination and immutable bytes/digest; acknowledging an older successful snapshot must leave later edits dirty. D1 remains the only parse/patch/serialize implementation.

Define the narrow Rust service API before those consumers:

```text
probe(path) -> ProbeResult                         // no mutation
bindStartup(owner) | inherit(owner, parent) -> ContextSnapshot
prepareActivation(owner, path) -> PreparedActivation
commitActivation(owner, activationId, expectedTag) -> ActivationResult
activationStatus(owner, activationId) -> ActivationResult
begin(owner, expectedTag, operation, legacyRoot?) -> OperationLease
readRaw(lease, selectedPath) -> RawDocument
writeRaw(lease, documentId, revision, destination, bytes) -> SaveReceipt
cancel(operationId); complete(lease); publicationAllowed(lease)
```

`owner` comes only from the host. Renderer methods omit it; IPC injects it. `ContextTag` contains process-session identity, window epoch and generation; `ContextSnapshot` adds profile/edition/root, detection fingerprint, config revision and capability snapshot. Leases privately capture roots/cache namespaces and accepted-write lifetime. `RawDocument` is a discriminated **raw-bytes** variant containing document ID, path, format hint and base64 bytes; hints do not certify format. It must bypass `decodeDocument`'s present “all base64 is binary AIV” branch. Rust tracks document owner/destination, not JSON sessions. Dialogs cancel before issuing writes. Save receipts include operation/document ID, submitted revision/digest and committed destination; target diagnostics do not prohibit preservation Save. Edition switches never change document format implicitly.

## Build, runtime and validation gates

Build the helper from the same core source/locked dependency graph as Tauri. One build tool emits the helper and expected manifest containing protocol major/minor, generated-contract hash, core-source/build identity, target architecture and metadata schema version. Use source/artifact hashes, not Git HEAD alone, for dirty builds. Rust contracts expose `Hello` with those identities, features and limits; require an exact packaged match before core operations. A mismatch produces an actionable backend-unavailable result, never a Node-policy fallback. Transport/protocol/unknown-outcome failures remain distinct from core domain results such as busy, corrupt and future-schema; none becomes an empty store. Tauri exposes the same initial capability contract without spawning a helper. Enable a pinned ts-rs export feature only for generation/tests so cross-crate DTOs can actually derive bindings; `cfg(test)` on a dependency alone will not do it. Local check mode regenerates to scratch and rejects stale/obsolete outputs.

Electron gets **one helper per main process**, launched by absolute bundled path with private stdin/stdout pipes, no shell/PATH/socket, and a hidden Windows process. Use bounded length-prefixed JSON frames, request IDs, stderr diagnostics, a bounded worker queue and a reader able to process cancellation while workers run. Initially cap raw documents at D1's 8 MiB default and frames at 12 MiB. Do not send A1's whole resource index or atlas. Reuse A1's cancellation token; blocking filesystem calls may finish before cancellation is observed. Once a write enters its commit section, finish or recover it and report its real result. Never kill the helper as ordinary cancellation or blindly replay writes. EOF rejects pending operations with an unknown-outcome diagnostic, invalidates backend epochs, and retains JS sessions. Rebind the original profile explicitly after recovery; never substitute the new default. Abandoned-lock removal remains offline maintenance after every participating backend is proven stopped.

Add the executable and manifest via Electron `extraResources`, outside ASAR, at `process.resourcesPath/core/toolkit-core-helper.exe` and `core/manifest.json`; run the build before both Electron dev and packaging, and check the actual directory/portable artifacts. Tauri links the core and needs no helper resource or native-package budget increase. Include actual helper dependency notices. The first artifact gate is Windows x64; inventory any other promised Electron targets before changing their support. Helper size/startup/IPC-copy overhead is presently **unmeasured**, not assumed free: measure a cold bind, 8 MiB open/save and cancellation latency from packaged artifacts before accepting the transport. Keep image transport expansion out of this slice.
